# データベース仕様

## 目的

本ドキュメントは、現行実装のデータ永続化方式（ファイルベースJSONストア）の仕様を示す。

- 定義の一次情報源は `要件定義書.md` です。本ドキュメントと齟齬がある場合は要件定義書を優先してください。
- 用語・命名は `用語集.md` に準拠します。
- 本書は実装（`src/types/domain.ts`・`src/lib/store.ts`・`src/lib/mock-data.ts`）の内容を正確に記述したものであり、サンプル・叩き台ではない。実装を変更した場合は本書も合わせて更新すること。

## 技術選定

CLAUDE.mdの「技術スタック」のとおり、クラウドDB（Prisma/PostgreSQL）は採用せず、大会当日インターネット接続なしで運営者のPC1台だけで完結して動作することを優先し、以下を採用する。

- 永続化方式: ファイルベースJSONストア。アプリ内のすべてのデータ（認証情報を含む）を1つのJSONファイル（`.data/store.json`）に保存する
- 読み書き実装: `src/lib/store.ts`（`loadStore()` / `saveStore()`）。Next.jsのRoute HandlerとServer Componentはプロセス上別モジュールインスタンスになり得るため、プロセスメモリ上の変数ではなくファイルを介して状態を共有する
- 保存先ディレクトリ: 環境変数 `LEAGUE_TABLE_DATA_DIR` で指定したディレクトリ配下の `.data/`（未設定時は `process.cwd()/.data`）。Electron版は起動時にOS標準のユーザーデータディレクトリ（`app.getPath('userData')`）をこの環境変数に設定する
- 日時: `Tournament.date` はJSTの日付（`YYYY-MM-DD`）をそのまま文字列で保持する（時刻情報・タイムゾーン変換は持たない）。バックアップの`createdAt`等は `new Date().toISOString()`（UTC）で保持し、表示時にアプリ層（`date-fns` + `date-fns/locale/ja`）でAsia/Tokyoに変換する
- 主キー: エンティティ種別ごとに異なる命名規則の文字列IDを用いる（「ID生成規則」参照。cuid等の統一規約はない）
- 参照整合性・カスケード削除・一意制約・各種ロック条件は、DBエンジンではなくすべてアプリケーションコード（`src/lib/mock-data.ts`・`src/lib/entrant-validation.ts`）側で担保する

## ストア全体形状

`.data/store.json` の中身は、以下の`Store`型（`src/lib/store.ts`）に対応する1つのJSONオブジェクトである。テーブルに相当する単位はこのオブジェクトのトップレベルキーであり、各キーは配列または連想配列を保持する。

```typescript
interface Store {
  auth: AdminAuth;
  session: Session | null;
  tournaments: Tournament[];
  categories: Category[];
  entrants: Entrant[];
  matches: Match[];
  standings: Record<string, StandingRow[]>; // キー形式は「標準順位表（standings）のキー形式」参照
  backups: BackupRecord[];
}
```

起動時にファイルが存在しない場合は、`src/lib/store.ts`の`seed()`が初期データ（管理者アカウント1件・サンプル大会2件等）を生成してファイルへ書き込む。

## エンティティ定義

以下は `src/types/domain.ts`（`AdminAuth`・`Tournament`・`Category`・`CategorySettings`・`Entrant`・`Match`・`SetScore`・`StandingRow`・`BackupRecord`）および `src/lib/store.ts`（`Session`）で定義されている型をそのまま転記したものである。

### auth（管理者アカウント / `AdminAuth`）

単一アカウントのみを保持する（配列ではなくオブジェクト1件）。追加作成用のサインアップ機能は設けない（要件定義書2.1）。

| フィールド | 型 | 備考 |
|---|---|---|
| id | string | ログインID。初期値はシード値（開発環境では`src/lib/store.ts`の`seed()`に直書き。Electron配布時の初期値は別途`README`等を参照） |
| passwordHash | string | bcryptjs（コストファクタ10）でハッシュ化したパスワード。平文は保持しない |

ログインID・パスワードの変更は `src/lib/auth.ts`の`updateCredentials()`が行う（A1画面のダイアログから利用）。

### session（現在のセッション / `Session`）

ログインしているブラウザセッションを**1つだけ**保持する（複数端末からの同時ログインには対応しない。後から発行したセッションが前のセッションを上書きする）。

| フィールド | 型 | 備考 |
|---|---|---|
| token | string | `crypto.randomUUID()`で発行するセッショントークン。Cookie（`admin_session`、`SESSION_COOKIE`定数）にそのまま保存する。未ログイン時はCookie自体が存在しない。 |
| role | `'admin'` \| `'viewer'` | `'admin'`は通常の管理者セッション、`'viewer'`はID・パスワードなしで入れる閲覧モード（書き込み系操作はすべて拒否） |

`session`が`null`の場合は未ログイン状態を表す。

### tournaments（大会 / `Tournament`）

| フィールド | 型 | 備考 |
|---|---|---|
| id | string | `tournament-${uuid}`形式（「ID生成規則」参照） |
| name | string | 大会名。1〜50文字（要件定義書3.1。`validateTournamentInput()`で検証） |
| date | string | 開催日。ISO 8601の日付のみ（`YYYY-MM-DD`） |
| location | string | 開催場所。1〜50文字（同上） |
| status | `'進行中'` \| `'終了'` | デフォルトは`'進行中'`。「終了」の間は大会情報・競技情報・選手(チーム)情報の編集、試合結果の入力・修正が不可（要件定義書2.1） |

削除時（`deleteTournament()`）は、紐づく`categories` / `entrants` / `matches` / `standings`のエントリをアプリケーションコードで連鎖的にフィルタ削除する（要件定義書2.1のカスケード削除要件）。

### categories（競技情報 / カテゴリ / `Category`）

用語集「競技情報 / カテゴリ」の注記に従い、1つの型に統一している。

| フィールド | 型 | 備考 |
|---|---|---|
| id | string | `${tournamentId}-${key}`形式（例: `tournament-xxxx-A`）。ランダムIDではなく大会IDとカテゴリキーから決定的に生成する |
| tournamentId | string | 大会ID |
| key | `'A'`〜`'J'` | カテゴリキー。1大会内で最大10個、`A`のみ必須 |
| name | string | カテゴリ名。1〜25文字、同一大会内で重複不可（要件定義書3.1。`createTournament()` / `updateTournament()`が呼び出す`validateTournamentInput()`で検証。対象は有効化されているカテゴリのみ） |
| enabled | boolean | 無効化（チェックを外して保存）すると、このカテゴリのレコード自体が`updateTournament()`内で削除される（専用の削除フラグではなく実削除） |
| settings | `CategorySettings` | 下記 |
| generationStatus | `'未生成'` \| `'生成済み'` | リーグ表・試合順・審判順が生成済みかどうか |

#### CategorySettings（競技情報の設定値）

| フィールド | 型 | 備考 |
|---|---|---|
| setCount | number | セット数。範囲1〜5、デフォルト1 |
| rankingMethod | `'勝敗方式'` \| `'勝点方式'` | デフォルト`'勝敗方式'` |
| winPoints | number \| undefined | 勝点方式の場合のみ使用。範囲0〜5、デフォルト3。勝敗方式の場合は`undefined` |
| drawPoints | number \| undefined | 同上。デフォルト1 |
| losePoints | number \| undefined | 同上。デフォルト0。制約: `winPoints > drawPoints > losePoints` |
| courtCount | number | コート数。範囲1〜5、デフォルト1 |
| maxEntrantsPerCourt | number | 1コート最大選手(チーム)数。範囲2〜10、デフォルト5 |
| leagueFormat | `'独立リーグ'` \| `'単一リーグ'` | デフォルト`'独立リーグ'`。`courtCount`が1の場合は常に`'独立リーグ'`として扱う（保存時にアプリ層で強制） |

検証ロジックは `src/lib/mock-data.ts`の`validateCategorySettingsInput()`（純粋関数）に実装されている。削除・変更のブロック条件（試合結果登録済み・選手登録済み・大会終了中）も同ファイルの`updateCategorySettings()`がアプリケーションコードとして担保する（DB側の制約機構は存在しない）。

### entrants（選手(チーム) / `Entrant`）

| フィールド | 型 | 備考 |
|---|---|---|
| id | string | `entrant-${uuid}`形式 |
| tournamentId | string | 大会ID（カテゴリ横断の一覧表示（A5画面）用に非正規化して保持） |
| categoryId | string | カテゴリID |
| name | string | 選手(チーム)名。全角10文字以内、同一カテゴリ内で重複不可（要件定義書3.3。長さ・重複チェックは`src/lib/entrant-validation.ts`の`validateEntrantAgainst()`で実施） |
| affiliation | string \| undefined | 所属。全角10文字以内、常に任意 |
| courtSelection | `'自動'` \| `'手動'` \| undefined | コート数2以上かつ独立リーグの場合のみ使用 |
| courtNumber | number \| undefined | 手動選択時のみ。範囲1〜カテゴリのコート数 |
| hasResult | boolean | この選手(チーム)が絡む試合結果が1件でも登録済みかどうか。trueの場合、カテゴリ・コート選択・コート番号の変更および削除をブロックする |
| displayOrder | number \| undefined | リーグ表・試合順表での表示順。リーグ表自動生成の実行時点でランダムに決定する（要件定義書3.4） |

### matches（試合 / `Match`）

リーグ表・試合順・審判順は要件定義書3.4〜3.6により常に一括生成・再生成されるため、1つの型に統合している（対戦カード＝リーグ表の1マス、`order`＝試合順、`refereeEntrantId`＝審判順を兼ねる）。

| フィールド | 型 | 備考 |
|---|---|---|
| id | string | 独立リーグ: `${categoryId}-c${courtNumber}-m${連番}`。単一リーグ: `${categoryId}-m${連番}` |
| categoryId | string | カテゴリID |
| courtNumber | number | 試合が行われる物理コート番号（独立リーグ・単一リーグいずれも実コート番号を持つ） |
| order | number | 独立リーグ: 同一カテゴリ・コート内での試合実施順。単一リーグ: カテゴリ全体の試合順（同一時間帯に複数コートで並行開催する試合は同じ値を共有する） |
| entrantAId | string | 選手(チーム)A |
| entrantBId | string | 選手(チーム)B |
| refereeEntrantId | string \| null | 審判。割り当てられる選手(チーム)がいない場合は`null`（画面側で「運営スタッフ」と赤字表示する。要件定義書3.6） |
| sets | `SetScore[]` | 下記。配列長はカテゴリの`setCount`と一致する |
| status | `'未入力'` \| `'入力済み'` | 結果入力状況 |

#### SetScore（セットスコア）

| フィールド | 型 | 備考 |
|---|---|---|
| scoreA | number \| null | 0〜999。`null`は未入力（要件定義書3.7の「未入力セット」） |
| scoreB | number \| null | 同上 |

生成（再生成）時は、対象カテゴリの既存`matches`エントリと対応する`standings`エントリを全削除してから再作成する（要件定義書3.4「リーグ表・試合順・審判順は常に一括で生成・再生成する」）。じゃんけんによる最終順位の手動確定結果は`matches`ではなく`standings`側（`StandingRow.rank` / `isTie` / `jankenPending`）に反映する。

### standings（勝敗表・順位表 / `StandingRow[]`）— 集計データ

勝敗表は`matches` + 試合結果から都度計算され（`src/lib/ranking.ts`）、試合結果保存時・じゃんけん確定時に`store.standings`へ書き戻してキャッシュする（要件定義書3.8の自動計算要件）。トップレベルの`standings`は「標準順位表キー → 行配列」の連想配列である（「標準順位表（standings）のキー形式」参照）。

| フィールド | 型 | 備考 |
|---|---|---|
| entrantId | string | 選手(チーム)ID |
| rank | number | 順位。タイの場合は同値を許容 |
| isTie | boolean | タイしているかどうか |
| wins / draws / losses | number | 勝ち数・引分数・負け数（自動計算） |
| setsWon / setsLost | number | 得セット数・失セット数 |
| setRate | number | セット率＝得セット数÷失セット数。失セット数0かつ得セット数>0の場合は`Infinity`（表示は「MAX」）、両方0の場合は0 |
| pointsFor / pointsAgainst | number | 得点・失点（全試合の合計スコア） |
| pointRate | number | 得点率＝得点÷失点。分母0の扱いは`setRate`と同様 |
| points | number \| undefined | 勝点方式の場合のみ使用。勝利勝点/引分勝点/敗北勝点を全試合分合計した値（順位決定の第一基準） |
| jankenPending | boolean \| undefined | 直接対決でも決着しない3者以上のタイがあり、じゃんけん結果の手動反映待ちであることを示す |

### backups（バックアップ履歴 / `BackupRecord`）

| フィールド | 型 | 備考 |
|---|---|---|
| id | string | `bk-${uuid}`形式 |
| createdAt | string | ISO 8601（UTC）のタイムスタンプ |
| trigger | `'手動'` \| `'ログアウト'` | 手動バックアップ、またはログアウト確認ダイアログで「バックアップする」を選んだ場合に作成される |

バックアップ本体（JSONスナップショット）は`store.json`とは別に、`backups`配下の`${id}.json`ファイルとして保存する（「バックアップファイルの形式」参照）。

## ID生成規則

| エンティティ | 形式 | 例 |
|---|---|---|
| tournaments | `tournament-${crypto.randomUUID()}` | `tournament-3f2a...` |
| categories | `${tournamentId}-${key}`（ランダムIDではなく決定的に生成） | `tournament-3f2a...-A` |
| entrants | `entrant-${crypto.randomUUID()}` | `entrant-9c1b...` |
| matches（独立リーグ） | `${categoryId}-c${courtNumber}-m${連番}` | `tournament-3f2a...-A-c1-m1` |
| matches（単一リーグ） | `${categoryId}-m${連番}` | `tournament-3f2a...-A-m1` |
| backups | `bk-${crypto.randomUUID()}` | `bk-7d4e...` |

## 標準順位表（standings）のキー形式

`store.standings`のキーは `${categoryId}:${courtNumber}` 形式の文字列である。

- 独立リーグ: 実際の物理コート番号（1〜5）をそのまま使う（例: `tournament-3f2a...-A:1`）
- 単一リーグ: カテゴリ全体で1つに統合するため、仮想的なコート番号として`0`を使う（例: `tournament-3f2a...-A:0`）

## バックアップファイルの形式

- 保存先ディレクトリ: `${DATA_DIR}/backups/`（`src/lib/store.ts`の`BACKUPS_DIR`。`ensureBackupsDir()`で遅延作成）
- ファイル名: `${id}.json`（例: `bk-7d4e....json`）
- 内容: `Store`型から`auth`・`session`を除いた部分（`tournaments` / `categories` / `entrants` / `matches` / `standings` / `backups`）をそのままJSON化したもの。認証情報・現在のセッションは対象外とする（バックアップ間で引き継がない）
- 保持件数: 最大20件。新規作成時に超過した分は、履歴配列の末尾（＝作成日時が最も古いもの）から履歴・ファイルの両方を削除する（`src/lib/backup.ts`の`MAX_BACKUPS`）
- 復元: 選択したバックアップJSONの`tournaments` / `categories` / `entrants` / `matches` / `standings`で現在のストアを上書きする。現在の`auth`・`session`・`backups`（バックアップ履歴一覧そのもの）は復元時も維持し、巻き戻さない（`src/lib/backup.ts`の`restoreFromSnapshot()`）

## 参照整合性・制約の担保方法

ファイルベースJSONストアはDBエンジンのような外部キー制約・CHECK制約・UNIQUE制約を持たないため、要件定義書で定められた制約はすべて`src/lib/mock-data.ts` / `src/lib/entrant-validation.ts`内のアプリケーションコードが実行時に検証する。主な例:

- カスケード削除: `deleteTournament()` / カテゴリ無効化時の`updateTournament()`
- 一意制約: 同一大会内のカテゴリ名重複禁止、同一カテゴリ内の選手(チーム)名重複禁止（`validateTournamentInput()` / `validateEntrantAgainst()`）
- 文字数上限の検証: 大会名・開催場所（1〜50文字）・カテゴリ名（1〜25文字）は`validateTournamentInput()`、選手(チーム)名・所属（1〜10文字）は`validateEntrantAgainst()`
- 変更・削除ブロック: 試合結果登録済み・選手(チーム)登録済み・大会終了中の各種ロック条件（`updateCategorySettings()` / `createEntrant()` / `updateEntrant()` / `deleteEntrant()` 等）
- 数値範囲・列挙値の検証: `validateCategorySettingsInput()`、各route.ts内のインラインチェック

唯一の例外として、カテゴリA（必須カテゴリ）そのものの存在チェックはサーバー側では行っていない（「カテゴリが1件以上存在すること」のみを検証し、どのキーかは問わない）。フォーム側でカテゴリAのチェックボックスを表示せず常に有効のまま送信することで担保している（`NewTournamentForm`）。
